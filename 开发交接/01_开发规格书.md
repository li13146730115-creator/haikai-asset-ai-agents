# 双智能体开发规格书 V2.4

本文件定义首期可编码的业务行为，与 `reference/openapi.json`、请求响应样例、参考服务及测试共同交接。V2.3保留为产品背景，V2.4的P0接口字段、金额单位、分页和错误码为本次开发基线。

## 1. 交接物与实际完成状态

| 交接物 | 开发拿到后可以做什么 | 当前状态 |
|---|---|---|
| 本规格书的8个P0场景 | 按前后置、交互、数据、分支及验收编码 | 规格已定义 |
| 11项接口＋32个Schema＋20个请求/响应文件 | 生成接口类型、搭建前端mock、配置工具参数、写接口用例 | 与参考实现对应 |
| `reference/service.py` | 运行合同核查、企业聚合、维度下钻和草稿幂等参考逻辑 | 虚构数据实现；可运行 |
| `reference/server.py` | 本机启动HTTP服务，供前端和中台联调 | 本地服务；不由GitHub Pages运行 |
| `reference/tests/` | 回归权限、财务、去重、状态、路由及HTTP分发行为 | 本轮执行结果见验证记录 |
| 中台节点规格及提示词 | 逐节点配置输入、输出、工具、澄清与失败分支 | 真实中台接入待实施 |
| 数据模型与适配清单 | 将真实表、API、SSO映射到既定业务接口 | 逻辑模型已定义；真实字段尚未取得 |

参考服务不是自然语言Agent。`/v1/agent-runs`接收已经识别好的结构化意图；客户中台仍需配置模型理解问题、实体消歧、槽位补齐和事实引用解释。参考服务不接真实数据库、不做真实财务核销、不发送催缴、不承担生产鉴权；这些边界不影响前后端先对着确定契约开发。

## 3. 所有开发统一遵守的协议

### 3.1 身份、金额、日期、版本

| 项目 | 明确定义 | 开发实现 |
|---|---|---|
| 用户身份 | 后端可信登录态；主体ID与访问项目由SSO/权限服务提供 | 请求JSON不能包含principal_id、tenant_id、scope_ref；未知字段返回422 |
| 责任关系 | SELF为当前用户负责的合同，ALL_VISIBLE为当前可访问合同 | 先访问权限，再项目/责任/企业筛选；空交集返回空，不能回退全量 |
| 金额 | 所有`*_fen`为人民币分整数；如10000000表示10万元 | 前端显示元/万元时换算；禁止浮点累计金额 |
| 比例 | `value_bps`为基点整数；8500表示85.00% | `value_bps/100`显示百分数；缺数值为null，禁止用`value || 0` |
| 截至日as_of | YYYY-MM-DD，业务时区由资管配置；到期当天不逾期 | 逾期判断为as_of > effective_due_date；天数按业务日差 |
| 数据可知时间 | captured_at为本次服务读取快照的时间；source_revision为源数据版本 | as_of只定义业务有效截止，不能冒充当时已知的历史报告 |
| 既有历史报告 | 保存分析结果和其source_revision、查询条件、规则版本 | 不重算覆盖旧报告；读取时重新鉴权；数据改变后下钻要求重核 |
| 首期查询集合 | 截至as_of已生效的有效叶子账单；R1包含其中未到期账单 | 暂不接受账期period参数，传入返回422；跨账期扩展需增加测试后发布v2契约 |
| 费用过滤 | filters.fee_codes限制财务账单集合 | R1/R2随费用过滤；R3—R6仍按入选合同的保证金/义务/准备/证据集合，UI写明 |
| 规则版本 | 首期参考实现只执行R-C01逾期、R-C02待分配核查 | 页面不得表述为“全部合同风险已检查”；其他规则按数据就绪启用 |

### 3.2 通用前端状态

IDLE（未查询）→RESOLVING（对象定位）→NEEDS_CLARIFICATION（待选择）→LOADING（分析中）→READY（成功）或EMPTY（无匹配）或ERROR（失败）。六维缺数是READY下的组件状态，不切成整页ERROR。

新查询有独立request序号；旧请求后返回时仅当前序号可写入UI。切换项目、企业、合同或截至日立即标旧结果“上次结果”，清除旧下钻与未确认动作，生成新查询，避免页面范围已变而金额沿用旧值。

按钮状态：LOADING期间禁用重复分析；下钻只在有analysis_id及合法维度时可点；草稿只有allowed_actions含SAVE_DRAFT才展示；确认提交期间禁用按钮并沿用同一Idempotency-Key。角色控制不能仅靠隐藏按钮，后端仍必须检查。

## 4. P0-01 合同定位与消歧

### 4.1 触发与角色

经办在合同台账输入“查一下远景的合同”；或者在合同详情点击“AI履约核查”。管理者也可以定位，但办理权限不同。合同详情携带contract_id仍需后端鉴权。

| 步骤 | 前端/中台输入 | 后端行为 | UI行为 |
|---|---|---|---|
| 1 登录上下文 | GET /v1/context | 返回当前主体、角色及访问项目；生产来自SSO | 范围栏显示“当前可见范围/本人负责” |
| 2 关键词检索 | POST /v1/resolve，object_type=CONTRACT，keyword=HT-A0 | 在可见合同内匹配编号或名称；最多50个候选 | 显示候选编号、名称；不能展示隐藏数量 |
| 3 消歧 | candidates多于1，status=NEEDS_CLARIFICATION | 不运行合同分析 | 用户必须选择一条；询问“请确认要核查哪份合同” |
| 4 唯一对象 | 稳定contract_id＋as_of | 交给P0-02；调用时重新授权 | 卡片标题固定合同号，后续续问绑定它 |
| 5 无结果 | candidates=[]，status=NO_MATCH | 不区分全局不存在与不可见对象 | “当前范围未找到可查询合同”，提供改关键词 |

请求和完整响应见接口目录resolveEntity。不要把第一个候选自动当作合同；若检索结果达到50条，提示缩小关键词，不将50理解为全量总数。

验收：demo-clerk-a检索HT-A0只得HT-A01、HT-A02，不能得到HT-A03；用户未选合同时不出现欠费结论。GET /v1/context无有效Bearer时返回401，停止后续取数。

## 5. P0-02 单合同欠费、逾期与到账核查

### 5.1 用户问题、前置与主流程

问题：“这份合同现在有哪些风险？”“还有没有缴费？”“客户说转过5000了，为什么还欠费？”前置为唯一合同、业务截至日、有效授权。中台调用createContractAnalysis，后端在同一事实快照下读取档案→叶子账单→核销/非现金/撤销→待分配到账→运行两条首期规则→生成不可变分析结果。

请求：`POST /v1/analyses/contract`，`{"contract_id":"HT-A01","as_of":"2026-11-08"}`，201返回ContractAnalysis。

### 5.2 结果卡字段与交互

| UI位置 | 响应字段 | 计算/显示要求 | 交互 |
|---|---|---|---|
| 卡片标题 | data.contract.number/name/project_id/effective_version | 显示合同号、项目、生效版本；不由模型改写 | 返回合同详情 |
| 范围与版本 | as_of、snapshot_id、source_revision、rule_version | “截至2026-11-08，本轮读取版本…” | 查看本次口径 |
| 应收 | data.financial.receivable_fen | 10000000分→100000.00元 | 展开纳入账单 |
| 已现金核销 | cash_allocated_fen | 8000000分→80000.00元；非现金结清另列 | 查看分配明细 |
| 未结 | unsettled_fen | 2000000分→20000.00元 | 未结账单筛选 |
| 逾期 | overdue_fen | 2000000分；账单最早/最大天数分别取明确字段，不混用 | 展开逾期账单 |
| 到账待核 | data.pending_receipts[] | 500000分到账待分配；单独展示，不减少欠费 | “生成核查草稿”，进入P0-06 |
| 风险 | data.rules[] | MATCHED为确认命中；PENDING_REVIEW为待核；不得合并成违约 | 展开rule_id和evidence_refs |
| 账单证据 | data.bills[] | 展示应收、核销、余额、有效到期日、逾期天数 | 展开allocations，显示真实付款日和核销有效日 |

模型解释使用服务端事实引用，例如“这份合同有逾期应收，另有到账待分配，建议先核实分配”。金额、天数直接由字段渲染；自由文本不新增金额或条款。

### 5.3 金额与日期规则

有效应收=纳入的EFFECTIVE叶子账单receivable_fen之和。现金核销=POSTED且effective_at≤as_of的CASH分配事件金额之和；撤销/退款使用负事件，与原事件同时保留，按一次净额求和；非现金结清同理独立汇总。单账未结=应收−现金−非现金。若现金或非现金净额为负，或两者大于应收，返回503 SOURCE_INCONSISTENT；不能悄悄截成0掩盖数据异常。

单账逾期=as_of>有效到期日时的未结；逾期天数=未结>0时max(as_of−有效到期日,0)。有效到期日由真实适配层先解析已批准生效的延期/宽限，草稿不得参与。待分配到账只显示有可靠合同关联、已核验、未分配>0且付款日在as_of以内的记录。

### 5.4 失败与验收

| 前提/触发 | 系统返回 | 页面行为 | 验收点 |
|---|---|---|---|
| HT-A01，11/8 | 应收10万、核销8万、未结/逾期2万；第三张账单8天；待核5000元 | 正常卡＋待核卡 | 对上3张账单及两条分配 |
| 同账单as_of=10/31 | 该2万到期但不逾期、0天 | 未结仍2万 | 不将到期当天算1天 |
| 无权HT-A03/不存在编号 | 404 NOT_ACCESSIBLE，同一对外文案 | 不显示旧合同结果 | 响应不含合同名/隐藏计数 |
| 撤销第二笔1万元现金核销 | 现金净额降为7万、余额3万 | 新查询值改变，旧报告保留 | 不删除原分配再重复负扣 |
| 分配超额/负净额 | 503 SOURCE_INCONSISTENT | 数据待核，不给余额结论 | 不用模型自行修正金额 |

## 6. P0-03 企业整体分析与六维

### 6.1 输入与数据组织

问题：“远景科技整体履约怎么样？”“哪几份合同拉低了回款？”“这两家企业分别怎么样？”请求createEnterpriseAnalysis；enterprise_ids可为一或多家，也可省略以分析全部当前范围主体。

默认role_scope=[SIGNATORY]。签约、代付、使用、担保、共同签约须有已核验合同—企业—角色关系；合同归属不能靠名称相似、同账户或同集团猜测。多企比较首期只展示并列指标和各自贡献，不生成综合信用分或未经可比性检查的排行榜。

集合计算顺序：访问项目∩请求项目∩责任关系∩企业角色匹配→唯一contract_id→有效叶子bill_id→合同指标→企业聚合。跨企业整体总计从去重合同集合计算；企业各行如共同关联同一合同，enterprise_totals_nonadditive=true，显示“企业关联规模不可直接相加”。

### 6.2 主卡、列表与雷达绑定

| 区域 | 响应字段 | 显示/操作 |
|---|---|---|
| 分析范围 | scope、query_context、as_of | 展示实际纳入项目、责任、主体角色、费用筛选；不声称全集团完整数据 |
| 整体总计 | data.financial、contract_count | 当前匹配合同全集去重的金额，不随分页改变 |
| 企业卡 | data.enterprises[] | 每企name、contract_count、financial、dimensions |
| 雷达/指标表 | dimensions[].id/status/numerator/denominator/value_bps | 雷达只绘有效维度；表格始终显示原始分子分母与单位 |
| 合同列表 | data.contracts[] | 合同、项目、负责人、金额、rules、handoff |
| 分页 | data.page.number/size/total/has_more | total只计当前可见匹配项；翻页重新请求，整体指标不变 |
| 维度点击 | analysis_id＋dimension_id | P0-05维度下钻；不让前端自行拉全部数据再拼合 |

### 6.3 六维资格集合、公式、舍入

| 维度 | 首期分子/分母 | 单位 | 适用/缺数判断 |
|---|---|---|---|
| R1 回款达成 | 账单现金净核销/有效应收 | 分/分 | 纳入有效账单含未到期；应收为0→NOT_APPLICABLE |
| R2 付款及时 | 到期账单中实际付款日≤有效到期日的现金净额，每账封顶/到期有效应收 | 分/分 | 付款日依据完整才算；部分合同依据不全→PARTIAL |
| R3 保证金覆盖 | ∑min(每合同有效保证金,每合同要求)/∑每合同要求 | 分/分 | 每合同先封顶，不能跨合同挪补；无源→UNAVAILABLE |
| R4 义务履行 | 已完成且有效证据的适用到期义务数/已发布必需到期义务数 | 项/项 | 只接受审核发布义务；客户与我方责任在适配层按模板分开 |
| R5 到期准备 | 前瞻1—90天内已完成核验准备项/适用必需准备项 | 项/项 | 首期90天固定；无准备项→NOT_APPLICABLE；真实没完成→0 |
| R6 证据完备 | 完成且已核验必需证据数/已发布适用必需证据数 | 项/项 | 有文件不等于完成核验；无适用证据→NOT_APPLICABLE |

每轴value_bps=ROUND_HALF_UP(num×10000/den)；保留整数。企业合并原始num、den后再舍入，不平均合同比例。PARTIAL仅保留已知合同的num/den，value_bps=null，并显示known_contract_count/eligible_contract_count；无源为UNAVAILABLE；全有源但den=0为NOT_APPLICABLE；全有源且num=0、den>0为COMPLETE、0。

### 6.4 验收例子

远景A三合同：应收20000000分、现金17000000分；R1=8500，R2=7750，R3=6667，R4=8000，R5=3333，R6=8000。仅A项目用户：只纳入A01/A02，应收18000000分、现金16000000分、R1=8889，响应不含HT-A03。海辰C：R2 PARTIAL/null、R3 UNAVAILABLE/null、R5 COMPLETE/0。

page_size=1翻到第2页：合同列表变化，整体总计和企业六维不变；不得对当前一行重新统计企业回款率。

## 7. P0-04 全局风险与未缴费清单

问题：“我现在有哪些合同有风险？”“我有哪些合同还没有缴费？”进入A2集合任务，允许无enterprise_ids。绝不先要求用户选一份合同。

| 输入/规则 | 明确定义 |
|---|---|
| list_type=UNSETTLED | 当前范围内unsettled_fen>0的合同，未到期也包括；卡片拆逾期与未到期 |
| list_type=RISK | 首期R-C01 MATCHED或R-C02 PENDING_REVIEW的合同；分别显示风险/待核标签 |
| responsibility=SELF | 可访问且responsible_id=当前主体的合同 |
| ALL_VISIBLE | 当前可见合同；不按用户职务推测更大的权限 |
| 排序 | 参考实现按contract_id升序，确保分页可复现；按风险/金额排序作为后续明确参数扩展 |
| 总计 | 仅匹配清单中的去重合同金额总计，分页前计算 |
| 清单点击 | 携带contract_id/as_of进入A1；重新鉴权，不带前端算出的金额当事实 |

若问“我的”但业务不能判断是本人负责还是全部可见，中台澄清“按本人负责还是全部可见”；已明确“我负责”的直接SELF。一线默认建议SELF但必须写在范围栏；管理者默认ALL_VISIBLE也要显示。

验收：demo-clerk-a的SELF欠费清单仅HT-A01；HT-A03虽由其负责但不在访问项目中，不能出现。filters.project_ids=[项目B]返回空清单与0总计，不回退A项目数据。

## 8. P0-05 指标穿透与证据

GET `/v1/analyses/{analysis_id}/details?dimension_id=R1&contract_id=HT-A01`。contract_id可省略，返回该分析纳入的每份合同贡献；必须已属于原analysis合同集合。响应返回同snapshot_id、每行numerator/denominator/status/source_refs、evidence和handoff。

| 动作 | 前端行为 | 后端行为 |
|---|---|---|
| 点击回款维度 | 抽屉显示各合同分子分母、指标、证据 | 从原查询条件及同源版本取合同贡献 |
| 点合同 | 将handoff.contract_id/as_of带到单合同入口 | A1重新授权并重新分析，不复制企业卡百分比作为结果 |
| 点证据 | 生产跳转通过资管证据定位服务实现 | source_id→权限核验→源账单/义务/附件；模型不能拼URL |
| 已更新事实 | 显示“数据已变化，请重新核验后查看明细” | 409 STALE_SNAPSHOT，不能将旧85%与新87.5%贡献拼在一起 |
| 不是本分析合同/无权 | 不展示任何内容 | 404 NOT_ACCESSIBLE |

首期参考证据提供source_type/source_id，未伪造资管真实跳转URL。正式接入时须由资管团队补授权定位，字段与现有详情页入口映射见适配清单。已保存报告读取旧值可用；要求动态明细时仍需同版本或重核。

验收：企业A的R1→A01为8000000/10000000分；带入A1仍为应收10万元、现金8万元。请求B01即使用户有权，也因不属于本次企业A分析而被拒绝。

## 9. P0-06 核查草稿、确认与幂等

用户在A1点“生成核查事项”，后端createReviewDraft保存当前analysis_id及source_revision。首期action_type固定PAYMENT_REVIEW；只创建核查事项，不核销资金。

| 状态/动作 | 输入 | 检查 | 输出/页面 |
|---|---|---|---|
| 生成草稿 | analysis_id/action_type/note | 原分析属于当前用户、单合同、当前源版本；CLERK或FINANCE | draft_id、合同、备注、source_revision、30分钟expires_at、DRAFT |
| 展示确认 | 无写动作 | 页面显示合同、金额事实、事项类型和备注 | “确认登记核查”，不显示“确认核销” |
| 首次确认 | expected_revision＋Idempotency-Key | 当前授权、角色、草稿归属、有效期、源版本、未提交 | SUBMITTED、work_item_id、financial_write_performed=false |
| 重复同请求 | 同key＋同draft/body | 先重新授权，再按key返回原结果 | 同一work_item_id，不重复生成 |
| 同key改对象/请求 | 已用于另一draft/body的key | 指纹不一致 | 409 IDEMPOTENCY_CONFLICT |
| 草稿已提交换key | 新key但草稿状态SUBMITTED | 状态校验 | 409 ALREADY_SUBMITTED |
| 草稿超30分钟 | 未提交且已过期 | 时间校验 | 409 DRAFT_EXPIRED；引导重新核验 |
| 事实变了 | 余额/数据源版本改变 | expected_revision及source_revision校验 | 409 REVISION_CONFLICT；重新分析后生成新草稿 |

管理者只读分析，不创建草稿。参考实现草稿归属当前创建人，其他人不能直接读/确认该草稿；生产协作转交需独立授权设计，不能凭角色为财务就绕过归属。

参考单号以MOCK-WORK开头、simulation=true、内存存储；生产须替换成资管事项接口和持久化事务。幂等表唯一约束tenant_id＋principal_id＋idempotency_key，保存request_fingerprint、work_item_id及响应；登记业务单和幂等记录应处于同事务/可靠消息流程。

验收：草稿和确认后A01余额仍为2万元；同key二次提交返回同单号；事实变化阻止旧草稿；已登记核查不代表逾期解除。

## 10. P0-07 重新核验与历史结果

POST `/v1/analyses/{analysis_id}/recheck`，请求体为空对象。当前登录人必须拥有原报告及仍有对应访问范围。服务重新使用原query_context读取当前事实，并创建新analysis_id/snapshot_id，不覆盖旧记录。变更项目/企业/日期使用新建分析接口，不能让recheck悄悄改变范围。

响应增加previous_analysis_id和changes：previous_source_revision、current_source_revision、source_changed。卡片展示“较上版数据变化/未变化”与新金额；业务风险依据新规则重新判断。

模拟：原系统已把5000元确认分配到A01第三张账单，其有效日期为11月7日。重核A01现金8.5万元、未结/逾期1.5万元；企业A回款率87.50%，付款及时仍77.50%；旧分析保留现金17万元及85%。参考测试通过适配器钩子模拟原系统变化，该钩子不注册为HTTP接口或模型工具。

当前权限/角色/项目发生变化→409 SCOPE_CHANGED，前端提示在新范围重新查询，不展示旧报告。当前用户不等于报告创建人→404 NOT_ACCESSIBLE。参考报告归属个人；跨用户共享报告不在首期能力中。

## 11. P0-08 自然语言与中台编排

### 11.1 中台必须实现的前后处理

用户问题→可信上下文→模型输出业务意图/原文实体/时间槽位→schema校验→T01对象解析→必要消歧→形成P0结构化请求→执行业务接口→校验结果→模型解释带事实引用→前端绑定结构化卡。

参考 `/v1/agent-runs` 用于验证中间的确定性编排，输入intent.object_level＋task和query；返回agent_id、trace、result、llm_called=false。它不接受一个自然语言字符串就假装已经完成模型理解。生产中台可以直接调用对应业务接口，也可调用此编排封装；必须完整实现前面的模型/澄清节点和后面的解释校验。

### 11.2 续问规则

| 续问 | 保留 | 清除/重建 | 动作 |
|---|---|---|---|
| “为什么回款低？” | 原analysis_id、query_context | 无 | R1下钻，引用合同贡献 |
| “只看A项目” | 企业和日期 | 原analysis_id、下钻和未确认草稿 | 新建企业分析，filters.project_ids=[项目A] |
| “这份合同呢” | 明确点击的contract_id/as_of | 企业维度结果作为A1依据的假设 | 新建单合同分析 |
| “现在再看” | 原查询条件 | 原source_revision | recheckAnalysis |
| “客户是否经营困难” | 当前事实 | 无依据的信用归因 | 说明本系统仅支持履约/经营指标，不推断外部经营状况 |
| “按上月比较”但无历史 | 企业 | 不伪造旧快照 | 提示历史数据未就绪，后续启用历史比较场景 |

### 11.3 可发布的验收门槛

每个任务至少收集一线、财务、管理者实际问法；核对路由、对象、日期、责任筛选及应澄清项，再检查工具调用和结果引用。财务数字与权限关键用例必须全部通过，不能靠语言相似度评分替代。参考单测验证确定性逻辑，真实模型准确率、平台超时降级和生产链路仍需客户环境评测。

## 12. 异常返回与前端文案

统一非2xx结构：error.code、message、retryable＋request_id。禁止失败时返回空合同数组冒充“没有风险”。

| HTTP / code | 发生条件 | 页面文案与后续 |
|---|---|---|
| 401 AUTH_REQUIRED | 登录失效/演示令牌不合法 | 登录已失效，请重新登录；停止取数 |
| 404 NOT_ACCESSIBLE | 合同/报告不存在、无权、非原分析对象 | 当前无法访问该对象；不透露具体原因 |
| 403 ACTION_FORBIDDEN | 角色不能登记 | 当前角色不可登记核查；可查看分析 |
| 422 INVALID_REQUEST | 未定义字段、错误日期、错误角色、分页越界 | 请检查查询条件；保留输入供修正 |
| 409 SCOPE_CHANGED | 访问/责任范围改变 | 范围已变化，请重新查询 |
| 409 STALE_SNAPSHOT | 旧分析要读当前已变化的明细 | 数据已变化，请先重新核验 |
| 409 REVISION_CONFLICT | 草稿源版本不一致 | 事实已更新，请核验后重新生成草稿 |
| 409 DRAFT_EXPIRED | 未确认草稿超过30分钟 | 草稿已过期，请重新核验 |
| 409 IDEMPOTENCY_CONFLICT | 同key不同请求 | 提交标识冲突，请刷新核查状态 |
| 409 ALREADY_SUBMITTED | 已提交草稿用新key再提交 | 该核查已登记，查看原事项 |
| 503 SOURCE_INCONSISTENT | 应收/分配不一致 | 财务数据待核，请联系财务核对；不显示错误余额 |

参考HTTP层另拒绝非法JSON、64KB以上请求体及不支持的路径。生产增加超时、限流、源组件不可用、请求取消和持久化故障处理；不得将这些错误转为业务缺数或0。
