# 数据模型、取数顺序与真实系统适配

这些是AI接入层的逻辑读取模型，不声称现有资管库存在同名表。开发可以先按此模型建立接口/读取层；资管团队把真实表或API映射进来，不需要让中台理解生产库的所有表。

## 1. 字段字典：主键、外键、类型和空值

生产所有记录均有tenant_id、source_version、source_updated_at；以下省略重复列。ID为稳定字符串，不用展示名称作为关联键。金额为BIGINT分，日期为业务DATE，时间为含时区TIMESTAMP。

| 逻辑实体 | 主键/外键 | 必需字段与类型 | 允许空/缺失的处理 |
|---|---|---|---|
| ai_contract | PK tenant_id+contract_id | number TEXT、name TEXT、project_id TEXT、responsible_id TEXT、status TEXT、effective_version TEXT、end_date DATE、timeliness_complete BOOL、guarantee_complete BOOL | 无responsible_id时不进入SELF；无有效版本则相关履约判断待核 |
| ai_enterprise | PK tenant_id+enterprise_id | name TEXT、verified_status ENUM | 统一标识可按权限另表保存；未经核验别名不自动合并 |
| ai_party | PK tenant_id+contract_id+enterprise_id+role+valid_from；FK合同/企业 | role ENUM、verified BOOL、valid_from DATE、valid_to DATE/null、basis_ref TEXT | valid_to可空表示仍有效；share缺失时只给不可加总关联规模 |
| ai_bill_leaf | PK tenant_id+bill_id；FK contract_id | fee_code TEXT、period_from/to DATE、receivable_fen BIGINT、effective_due_date DATE、effective_at DATE、status ENUM、is_leaf BOOL、parent_id TEXT/null | 缺到期日仍可显示余额，但生产必须将逾期组件标缺数；参考fixture只含完整日期 |
| ai_allocation | PK tenant_id+allocation_id；FK bill_id | amount_fen BIGINT带符号、kind CASH/NONCASH、actual_paid_at DATE、effective_at DATE、status POSTED/VOID、reverse_of TEXT/null | NONCASH实际付款日不作现金及时性；CASH付款日缺失→timeliness_complete=false |
| ai_receipt_pending | PK tenant_id+receipt_id；FK verified_contract_ref/null | amount_fen BIGINT、unallocated_fen BIGINT、payer_enterprise_id TEXT、actual_paid_at DATE、verified BOOL | 无可靠合同关联不放进单合同待核到账；不按姓名猜匹配 |
| ai_guarantee | PK tenant_id+guarantee_id；FK contract_id | required_fen BIGINT、valid_held_fen BIGINT、verified BOOL、effective_from/to DATE | 无来源不能生成0保证金；担保函等形式应在适配层按审核条件标准化 |
| ai_obligation | PK tenant_id+obligation_id；FK contract_id | required BOOL、completed BOOL、verified BOOL、review_status ENUM、due_date DATE、obligor ENUM、template_version TEXT | 未审核不进入资格集合；条件/期限不清标候选待核 |
| ai_preparation_item | PK tenant_id+item_id；FK contract_id | required/completed/verified BOOL、review_status ENUM、due_date DATE、obligor ENUM | 必需项模板缺失不能默认为无适用项；生产需覆盖状态 |
| ai_evidence_item | PK tenant_id+evidence_id；FK contract_id/obligation_id | required/completed/verified BOOL、review_status ENUM、source_ref TEXT、valid_until DATE/null | 缺证记录明确存在且有效，才可判未完备；不是“没查到=未履行” |
| ai_analysis | PK tenant_id+analysis_id | principal_id TEXT、scope_hash TEXT、query_json JSON、source_revision TEXT、snapshot_id TEXT、result_json JSON、created_at TIMESTAMP | 保存不可变结果；撤权后读取拒绝，不能靠存档绕权限 |
| ai_review_draft / ai_submission_key | draft PK tenant+draft_id；幂等PK tenant+principal+key | analysis_id、source_revision、state、expires_at、fingerprint、work_item_id、response_json | 草稿与幂等登记持久化；原业务单与幂等写入有原子性或可靠消息保障 |

参考fixture用`contracts/parties/bills/allocations/...`集合保存这些字段；字段名映射见reference/fixture.json。主业务接口不把读模型内部表名暴露给模型。

## 2. 必须避免的一对多放大

错误方式：合同表join主体关系join账单join核销后直接sum，应收会同时被多个主体和多笔分配重复计入。

正确方式：先把每张账单的分配事件汇总到bill_id，再回连唯一叶子账单；合同/企业使用EXISTS筛选关联合同；需要显示每企关联规模时单独按企业分组，但跨企业总计依然回到唯一合同集合。

下面SQL只说明逻辑读取层算法，实际数据库需映射字段。:principal_id、:tenant_id由后端可信上下文绑定，不从模型接受；:as_of、:enterprise_id、:fee_code为校验后的业务参数。

```sql
WITH eligible_contract AS (
  SELECT c.contract_id
  FROM ai_contract c
  WHERE c.tenant_id = :tenant_id
    AND EXISTS (
      SELECT 1 FROM trusted_user_project p
      WHERE p.tenant_id = c.tenant_id
        AND p.principal_id = :principal_id
        AND p.project_id = c.project_id
    )
    AND (:self_only = 0 OR c.responsible_id = :principal_id)
    AND (:enterprise_id IS NULL OR EXISTS (
      SELECT 1 FROM ai_party r
      WHERE r.tenant_id = c.tenant_id AND r.contract_id = c.contract_id
        AND r.enterprise_id = :enterprise_id AND r.role = 'SIGNATORY'
        AND r.verified = 1 AND r.valid_from <= :as_of
        AND (r.valid_to IS NULL OR r.valid_to >= :as_of)
    ))
), allocation_per_bill AS (
  SELECT bill_id,
    SUM(CASE WHEN kind = 'CASH' THEN amount_fen ELSE 0 END) AS cash_fen,
    SUM(CASE WHEN kind = 'NONCASH' THEN amount_fen ELSE 0 END) AS noncash_fen
  FROM ai_allocation
  WHERE tenant_id = :tenant_id AND status = 'POSTED' AND effective_at <= :as_of
  GROUP BY bill_id
), bill_fact AS (
  SELECT b.bill_id, b.contract_id, b.receivable_fen, b.effective_due_date,
    COALESCE(a.cash_fen, 0) AS cash_fen,
    COALESCE(a.noncash_fen, 0) AS noncash_fen,
    b.receivable_fen - COALESCE(a.cash_fen, 0) - COALESCE(a.noncash_fen, 0) AS balance_fen
  FROM ai_bill_leaf b
  JOIN eligible_contract e ON e.contract_id = b.contract_id
  LEFT JOIN allocation_per_bill a ON a.bill_id = b.bill_id
  WHERE b.tenant_id = :tenant_id AND b.status = 'EFFECTIVE'
    AND b.is_leaf = 1 AND b.effective_at <= :as_of
    AND (:fee_code IS NULL OR b.fee_code = :fee_code)
)
SELECT contract_id, SUM(receivable_fen) AS receivable_fen,
  SUM(cash_fen) AS cash_allocated_fen, SUM(noncash_fen) AS noncash_settled_fen,
  SUM(balance_fen) AS unsettled_fen,
  SUM(CASE WHEN effective_due_date < :as_of THEN balance_fen ELSE 0 END) AS overdue_fen
FROM bill_fact GROUP BY contract_id;
```

以上COALESCE只用于“覆盖完整且确实不存在分配行”的情况；若分配源根本没接通或水位过期，不能借COALESCE把未知改成0。生产需在执行该SQL前检查数据源覆盖和一致性，按组件返回PARTIAL/UNAVAILABLE/ERROR。

R2在同账单粒度统计actual_paid_at≤effective_due_date的现金净分配，逐账封顶后再汇总；R3逐合同min(held,required)后汇总；R4—R6按已发布适用项计数。不能把账单比例简单平均成企业比例。

## 3. 一致性、时间与版本的生产实现

参考服务在单进程锁内读取完整内存fixture，source_revision为该fixture内容摘要。正式实现应选择一种一致快照机制：数据库只读事务快照，或经核对的读取模型批次版本。T02事实、T03规则和T04/05指标消费同一快照引用；证据至少保留源记录ID及版本。

as_of是业务有效截止，captured_at是本次取得这些事实的时间。财务在11月9日补录一笔11月7日生效的分配后，11月8日口径重新计算可以改变；它是“按当前已知事实重核11月8日”，不能冒充11月8日当时系统已知情况。要看当时报告必须读取旧snapshot/result，不从当前库反推。

正式数据覆盖应至少细化为finance、contract_version、parties、guarantee、obligation、preparation、evidence各自状态和水位。参考fixture完整财务源、R2/R3的合同覆盖标记只是最小联调样本，不能代替生产的数据完整度服务。
